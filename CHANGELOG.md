# Changelog

Every entry that changes a security property is tagged **[security]**, so an app pinned to an older version can see what a bump fixes.

## Unreleased (2026-10-13, auth batch 5)

### Added

- auth: `DataHooks.SessionEnded`, a hook for every session ending, with a typed `SessionEndReason` (closed set: sign-out, revoke, revoke others and all, admin, impersonation stopped, ban, password changed/reset/set, credential changed, token reuse, provider logout, user deleted, expired). `Auth.EndSession` and `Auth.EndUserSessions` take the reason (`DeleteSession`/`DeleteUserSessions` report `SessionEndUnspecified`); the hook runs once per session inside the ending transaction. A hook cannot refuse an ending: on an error the attempt is rolled back, the session ends again without hooks, and security kind `session.end_hook_failed` (`SecuritySessionEndHookFailed`, attrs `session_id`, `reason`, `error`) reports the lost hook. The expiry sweep reports per batch of 500 through the optional store upgrade the SQL and memory stores implement; Redis/TTL stores and stateless mode have the gaps documented in `docs/concepts/sessions.md`. Core, admin, password, twofactor, email, scim, sso and oauthprovider pass their reasons.
- plugin/webhook: `session.revoked` now covers every session ending (admin revoke, sign-out everywhere, ban, password change, token-reuse theft, user deletion, expiry sweep) with a `reason` in `webhook.SessionRevokedData`, and a self sign-out sends exactly one event; the earlier operation-hook path is removed.
- auth: session tasks. `SessionTasker`, `SessionTask`, `Auth.CompleteSessionTask`, `CurrentSessionTasks`, `TaskSetupMFA`, error `auth.session_task_pending` (403, `*SessionTaskError` in Go), `SessionResult.tasks`, `Session.Tasks`, migration `0008_session_tasks`. A session with tasks pending reaches only the operations its tasks allow plus session read, sign-out and refresh; `authhttp.RequireUser` answers 403 for it. Guide `docs/concepts/session-tasks.md`, example `examples/session-tasks`.
- auth: `WithTokenRotation(TokenRotation{Grace})`, which rotates the session token on every sliding refresh. It adds the optional store upgrade `SessionTokenRotator` (implemented by the SQL store, the memory store and contrib/redis) and `sessiontest` cases for it. Also new: migration `0009_session_previous_token`, `DefaultTokenRotationGrace`, `MaxTokenRotationGrace`, security kind `SecuritySessionTokenReuse` (`session.token_reuse`) and `AttrSessionID`. Example `examples/token-rotation`.
- auth: `Effect.Replaces` and `Effects.ReplaceSessionOf`, for a token re-issued for the same sign-in.
- Two-factor: several second factors per user (authenticator app, delivered codes, security keys), picked at the challenge with `method`; security keys (WebAuthn, roaming or platform) as a second factor through `twofactor.WithSecurityKeys(pk.SecurityKeys())`, stored in the passkey plugin's own `auth_passkey_security_key` table so a key never signs in alone; `twofactor.remove-factor` removes one factor (the last turns two-factor off); adding a factor while one is on needs a current factor as `proof`. Existing single-factor users are unchanged. Example `examples/two-factor-security-key`.
- Two-factor: `twofactor.RequireEnrolment(rule)` makes a second factor mandatory for the users an `EnrolmentRule` names: their session has the `setup-mfa` session task pending (only status, enroll, confirm and security-key registration reachable) until a factor is on, then a new token is issued and the old one stops working.
- organization: verified domains (`organization.Domains`). An organization adds an email domain, proves it with a DNS TXT record (replaceable `DomainVerifier`; opt-in `TrustVerifiedEmail`) and picks an enrollment mode: `manual_invitation`, `automatic_invitation`, `automatic_suggestion` (admin-approved membership requests) or `automatic_join`. Only a verified email at a proved domain enrolls; a proved domain belongs to one organization; public mail domains are refused. Ten new operations, two tables (migration `0007_organization_domains`). Example `examples/org-domains`.
- organization: `(*Plugin).PermissionsOf(ctx, orgID, role)` returns the union of the permissions a role's parts grant (static and dynamic roles), deduplicated and sorted.
- `metadata` plugin: public, private and unsafe JSON documents per user. `GET /metadata/get` and `POST /metadata/update` (RFC 7396 merge patch on unsafe, size-capped by `WithUnsafeMaxSize`, rate-limited per user by `WithUpdateRate`, optional `WithUnsafeCheck`); `Get`, `Set`, `Merge`, `PublicOf` and `SessionExtras` (for `auth.WithSessionExtras`) from Go; opt-in `metadata.admin-get` / `metadata.admin-update` decided by a `metadata.Authorizer` (`WithAdmin`), with no import of plugin/admin. Stored in its own table `auth_user_metadata` (engine document type), never on `auth_user`, so private metadata is not loaded with every request's user. Error codes `metadata.invalid` (400), `metadata.too_large` (413), `metadata.forbidden` (403). Example `examples/user-metadata`, guide `docs/plugins/metadata.md`.
- jwt: named token templates (`jwt.WithTemplate`, `POST /jwt/template`, the shape of a `getToken({ template })` call) signed with a published key, an HS256 shared secret (`HMACKey`: at least 32 bytes, never published, refused by every `Verifier`) or a receiver-issued key (`PrivateKey`); `jwt.ClaimSource` for claims whose lookup can fail; `jwt.UserClaim` for a per-user JSON document such as plugin/metadata's public metadata; `jwt.VerifyHS256`; presets for Supabase, Hasura, Convex and Firebase custom tokens in `plugin/jwt/jwtpreset` (opt-in example conventions); the active organization's id, slug, role and permissions as a claim in `plugin/organization/orgjwt`, with the permissions source pluggable (`orgjwt.Permissions`) for apps on a custom authorizer. New error code `jwt.unknown_template` (404). Example `examples/jwt-templates`.
- [security] `plugin/samlidp` (own module): the app as a SAML 2.0 identity provider. IdP metadata, SP-initiated SSO in the HTTP-Redirect and HTTP-POST bindings with an HTTP-POST response, opt-in IdP-initiated sign-on (`ServiceProvider.AllowIdPInitiated`, a POST that needs the session and the origin check). SPs are registered in code (`ServiceProviders`) or looked up at run time (`WithServiceProviderStore`), each with its entity ID, an exact ACS URL allowlist, optional certificates for signed AuthnRequests (`RequireSignedRequests`, `WantAuthnRequestsSigned`), a NameID format (persistent, email, transient, unspecified) or `NameID` func, and an `Attributes` func (`DefaultAttributes`). Responses and assertions are signed with any RSA or ECDSA `crypto.Signer` (RSA-SHA256 / ECDSA-SHA256, exclusive C14N); the assertion's only Audience is the SP entity ID, Recipient/Destination the ACS URL, InResponseTo the request ID. Request IDs are single use (verification rows in a store that refuses duplicates, or `WithRequestIDGuard`), IssueInstant must be within `RequestMaxAge`/`ClockSkew`, a signed request must name this IdP as Destination, POST signatures are checked with goxmldsig (signature wrapping refused) and SHA-1 is refused. A signed-out browser is sent to `LoginPage?return_to=…` (with `prompt=login` for ForceAuthn) and never gets an assertion; IsPassive answers NoPassive. A session waiting for its second factor or with a session task pending is treated as signed out: sent to the login page, never asserted. `Access` is the authorization seam per user and SP. Single logout is not implemented yet. Guide `docs/plugins/samlidp.md`, example `examples/saml-idp`.
- plugin/webhook (own module): signed outgoing webhooks (Standard Webhooks: webhook-id, webhook-timestamp, webhook-signature, HMAC-SHA256, whsec_ secrets) for user, session, identity and security events, plus `Publish` for app events; rows written in the event's transaction, first send after the commit, retried by `auth maintain` with exponential backoff and jitter, dead-lettered after `MaxAttempts`, `Deliveries` and `Replay`, a 410 disables the endpoint, secrets sealed through `auth.Sealer` with rotation, an SSRF guard on the dialled address (`AllowPrivateNetworks` for local development); package `plugin/webhook/signature` (standard library only) verifies on the receiving side. Guide `docs/plugins/webhook.md`, example `examples/webhooks`.
- React kit: admin dashboard hooks (`useAdminPermissions`, `useAdminUsers`, `useAdminUser`, `useAdminUserSessions`, `useAdminTwoFactor`, `useImpersonation`, `useAdminActions`, `ADMIN_QUERY_ROOT`) and pure pager helpers (`pageItems`, `pageRange`, `lastPage`, `adminUsersCall`).
- React kit registry: `AdminUsersTable` (search, role/status filters, sort, numbered pagination with page-size choice, `/` and arrow-key shortcuts), `AdminUserDetail` (sessions with revoke, ban/unban, role, set password, second factor pause/resume/reset, impersonate, delete with confirmation; each action gated by `admin.has-permission`), `ImpersonationBanner`, and the `table` primitive. Demo route `/admin`; the demo seeds an admin, a second password user and 64 directory users.
- `admin.UserSummary` carries `email` (primary address, else the earliest email identity, else empty) and `roles`, in `users`, `search-users` and `user`, loaded for the whole page with one query each.
- React kit: session tasks (`useSessionTasks`, `SessionTaskRedirect`, `useSessionTaskRedirect`, `paths.setupTwoFactor`) and the `TaskSetupMFA` registry page for `twofactor.RequireEnrolment`.
- React kit: security-key enrolment in `TwoFactorSetup` (a security keys section, `securityKeys` prop; also the standalone `SecurityKeys` component): add with proof from another factor, recovery codes shown once for a first key, remove with a code or a key tap; `TwoFactorChallenge` answers with a security key and picks between code factors.
- React kit: verified organization domains (`useOrganizationDomains`, `useMembershipRequests`, `useDomainSuggestions`, `useOrganizationDomainActions`) with the `OrganizationDomains` and `DomainSuggestions` registry components.
- React kit: `useGetToken({ template? })` for jwt tokens and templates, cached until shortly before expiry; `useAdminUserMetadata` and a metadata section on `AdminUserDetail`.
- React demo: wires security keys, forced two-factor setup for `mfa@example.com`, organization domains (verified through the admin's own address, no DNS) and user metadata.
- integration: `TestWireContract` walks the new operations (metadata, organization domains, two-factor security keys and remove-factor, jwt templates) and gives a `json.RawMessage` field an object; `TestConfigEdge` covers the new options, with builders for `metadata.Option`, `webhook.Option` and `orgjwt.Option`.

### Changed

- orgjwt: `orgjwt.Claims` returns `(jwt.ClaimsFunc, error)` and refuses `orgjwt.Permissions(nil)` (or a nil source) when the app starts (and returns a func that fails every token, so ignoring the error is still loud), naming the option, instead of failing every token call at request time (unreleased API).
- [security] auth: under `WithTokenRotation`, a replaced session token presented after its grace window revokes the session for every holder and emits `session.token_reuse` at alert.
- [security] authhttp/auth: under `WithMultiSession`, a token re-issued for the same sign-in is no longer kept as a second account cookie and no longer counts against the device cap. The re-issues covered are a refresh that changed the token, a second-factor promotion, a completed session task and a stateless reseal.
- [security] Two-factor: adding a second method while two-factor is on now needs a current factor as `proof` (a code, a recovery code or a security-key assertion), on `enroll` and on `security-key-register-finish`; without it the answer is `twofactor.proof_required` (400). Before, enroll over a factor that was on was refused outright, and a stolen fresh session could otherwise plant a factor of its own. `enroll` of the method the user already has still answers `twofactor.already_enabled`.
- jwt: `JWKSPath("/template")` is refused, and `Operations()` lists three operations (two under `RemoteJWKS`).

### Changed

- plugin/oauthprovider: `ClientMetadata` is the registration input only; `client_name`, `grant_types`, `response_types`, `token_endpoint_auth_method` and `scope` are now `omitempty`, so the OpenAPI document and the TypeScript client (`OauthproviderClientMetadata`) leave them optional, as the provider defaults them. `Client` now embeds the new `RegisteredMetadata`, the same fields with those five always present, so the RFC 7591 registration answer still carries every registered value. Promoted fields (`c.Name`, `c.GrantTypes`, …) are unchanged; code that named the embedded field (`Client{ClientMetadata: m}`, `c.ClientMetadata`) now uses `RegisteredMetadata` and converts with `oauthprovider.RegisteredMetadata(m)`.
- plugin/deviceauth: `CodeRequest.UserID` is Go-only (`json:"-"`): the OpenAPI document and the TypeScript client no longer offer `user_id`, which every transport refused. `dp.Code` from Go still binds the code; the JSON route refuses `user_id` as an unknown field, and the RFC handler now ignores it as an unrecognized parameter (RFC 6749 section 3.2) instead of answering `invalid_request`. An operation reached through `Operation.Invoke` with a decoder that sets it is still `device.invalid_request`.

### Core

### Pluggable sessions (2026-09-30)

- `auth.SessionStore`: sessions go through one interface. The `auth_session` table stays the default (still one query per lookup, still inside `a.Tx`); `auth.NewMemorySessionStore()`, `redisrate.NewSessionStore` in `contrib/redis`, or any custom store plug in with `auth.WithSessionStore`. A store sees only token hashes. `github.com/ubgo/auth/sessiontest` is the conformance suite every store passes.
- `auth.SessionCache` with `auth.WithSessionCache`: skips the lookup for a short time. `auth.NewSnapshotCache` (an AES-256-GCM copy the client carries in `__Host-auth_session_cache` or `Auth-Session-Cache`, bound to its token), `auth.NewMemorySessionCache`, `redisrate.NewSessionCache`. One minute by default, fifteen at most, never renewed without the store; a second-factor session is never cached. New effects `EffectCacheSession` and `EffectClearCache`, and `Request.CachedSession`.
- `auth.WithStatelessSessions`: the token carries the session, sealed. The user is still loaded per request, so bans apply at once, and `auth_user.sessions_valid_after` makes "sign out everywhere" and password resets refuse older tokens. Listing or ending other sessions answers `409 auth.sessions_unavailable`.
- `auth.WithSessionPolicy` and `auth.ByCredential`: a lifetime per session, chosen at creation (for example browsers 30 days, apps a year), stored in the new columns `idle_seconds`, `refresh_seconds` and `max_expires_at`, capped at `auth.MaxSessionLifetime` (400 days). `Request.Delivery` (filled by `authhttp` from `Auth-Token-Mode`) tells the policy that an app asked for a bearer token at sign-in, before it holds one; without it an app's first session got the browser lifetime.
- Migration `core/0003_session_lifetimes` adds those columns and `auth_user.sessions_valid_after`.
- `authui` applied no effects on `GET /settings` or a failed form, so a sliding refresh or a cache copy from those pages was lost; both now apply them.

### Pre-release audit (2026-09-29)

Every package was brought to full statement coverage, merged across the unit and integration suites (`task cover`), and every database failure of every operation is now proven to reach the caller (`sweepFaults` in the integration suite fails each database call in turn). The pass found and fixed these defects before any release:

- **[security]** The in-memory rate store could be reset by flooding: past 10,000 keys, its cleanup used the window of whichever call triggered it, so short-window keys erased long-window counts. Each entry now keeps its own window.
- **[security]** Password sign-up answered differently for a taken and a free value of a custom identifier kind whose plugin cannot deliver, which revealed which accounts exist. Both now answer the same.
- **[security]** A magic-link kind whose plugin cannot deliver failed only for identifiers that have an owner, which revealed which accounts exist. `magiclink` now refuses such kinds at `auth.New` (`ErrNoKinds`, `ErrBadKinds`).
- **[security]** Confirming an email change could skip the undo link to the old address when the new address's row sorted first (an older row, or equal timestamps on MySQL), so a stolen session's change could not be undone. The old primary is now found in its own pass.
- Lists of identities, sessions, OAuth accounts and API keys ordered by creation time alone, so rows created in the same instant came back in a different order on each engine. They now break ties by id.
- Accepting an organization invitation as an existing member failed on Postgres, because a caught duplicate insert had aborted the transaction. Membership is now checked first.
- **[security]** Undoing an email change swallowed a failed lookup, so it could report success while the replacing address stayed on the account. It now returns the error.
- **[security]** An operation run inside an outer `a.Tx` set its session cookie even when that transaction rolled back, replacing a valid cookie. Effects now reach the response only when the outermost transaction commits.
- **[security]** The ready-made pages sent `Referrer-Policy: no-referrer`, under which browsers send `Origin: null` on form posts, so the origin check refused every form in a real browser. They now send `same-origin`.
- Identifier kind names longer than 28 characters produced index names that MySQL refuses and Postgres truncates into collisions; `auth.New` now refuses them.
- Adding an email or phone number swallowed a failed lookup and could insert a duplicate row; phone resend answered OK when the database failed; passkey sign-in reported a database failure as a bad passkey; the admin user search showed an empty page on a database failure. All now return the error.
- An API key sent as a bearer token crashed an `Auth` built without a database; it now returns `auth.ErrNoDatabase`.
- `authhttp.WriteError` did not set `Retry-After` on a rate-limited error, and `authhttp.RequireScope` answered 403 where no credential was presented; it now answers 401, and 403 only when a principal lacks the scope.
- **[security]** The JWT verifier decoded base64 leniently, so one signature had several valid spellings and a token could be re-encoded without the key; it now decodes strictly.
- `jwt.Verified.ExpiresAt` was in local time; it is UTC like every other time the library returns.
- The phone plugin's default text always said the code expires in 10 minutes, whatever `WithCodeTTL` set.
- The per-process rate-limit warning printed on every `auth migrate` and `auth sweep`; it now prints on the first counted request. `a.Sweep` now clears the database rate store whenever its table exists, and `auth sweep` reports it.

### Security properties this version holds

- **[security]** Every secret comparison is constant-time; a source guard fails the build otherwise.
- **[security]** Sign-in runs one argon2 check on every path, known account or not; pinned by a source guard and a timing test.
- **[security]** Only verified identities match a person: sign-in prefers the verified row, invitations and social linking require verified addresses on both sides.
- **[security]** Tokens are single use under concurrency; the database, not Go, picks the one winner.
- **[security]** Failed guesses (phone codes, TOTP codes, sign-in attempts) are counted outside the transaction the failure rolls back.
- **[security]** Values are normalized in Go and compared byte-exactly on every engine; MySQL tables are `utf8mb4_bin`.
- **[security]** A pending second-factor session signs nobody in, and passing the factor issues a new token.
- **[security]** A magic link reaches only a verified owner, or with SignUp an identifier nobody claimed; it is single use and short-lived.
- **[security]** A banned user's sessions stop on the next request; the last admin cannot be removed; admins cannot be banned.
- **[security]** An impersonation session lasts at most an hour, is recorded on the session row and shown in the user's session list, cannot target an admin, and cannot change the password, addresses, factors or passkeys.
- **[security]** In host-only mode a `__Secure-` session cookie planted by a sibling subdomain is ignored.
- **[security]** An API key cannot use any auth operation, is ignored in a cookie, and stops with its user's ban.
- **[security]** A JWT is EdDSA-only, never outlives its session, and names the admin (`act`) under impersonation.
- **[security]** The ready-made pages refuse every cross-site form POST, sign-in included, which stops login CSRF.
- **[security]** Passkeys require user verification, and a credential whose sign count goes backwards (a clone) is refused.
- **[security]** Passwords and tokens print as `[redacted]` through fmt, slog and JSON.
